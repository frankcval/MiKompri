## Condiciones antes de operaciones cloud

Para el negativo de scope, el primer request `diagnostic_only` conserva `access_as_user` en el token. Se autoriza dentro de este recurso QA ya previsto reducir **temporalmente** el grant SPA→API a `diagnostic_only`, solicitar token nuevo, comprobar política y restaurar `access_as_user diagnostic_only` al terminar. No se revocan tokens/productivos ni cambian permisos de ningún usuario MiKompri. Registrar esta condición del ensayo y la restauración, incluso si el negativo queda inconcluso por caché/consentimiento.

Ampliación previa a consentimientos Graph: la lectura de `identity/identityProviders` devuelve 403 aunque el administrador QA tenga Global Administrator y el token CLI incluya Directory.AccessAsUser.All. Se prevé un **grant delegado temporal para ese administrador solamente**, en el service principal Azure CLI del tenant QA, con `IdentityProvider.ReadWrite.All`, `EventListener.ReadWrite.All` y `User.ManageIdentities.All`. Propósito: configurar/inspeccionar proveedores, flujo y probar colección identities; no se añaden permisos al tenant workforce ni a las APIs MiKompri. Coste: sin secreto/hosting adicional. Almacenamiento: consentimiento en CIAM; token solo en memoria CLI. Limpieza: eliminar exactamente ese grant QA al terminar. Se comprobará el scope del token nuevo; el rol por sí solo no se presenta como permiso OAuth suficiente.

La consulta encuentra cero service principals Azure CLI en el CIAM recién creado: para el grant se prevé instanciar únicamente ese service principal público de Microsoft en QA (sin nuevo registro global, secreto ni modificación de la aplicación Microsoft). Se eliminará junto con el grant al retirar el QA.

Resultado de esa ruta: AADSTS65002 al solicitar scopes adicionales para un cliente first-party; grant temporal retirado inmediatamente. No se cambia ninguna política/preautorización de Microsoft para evitar ese control. Como alternativa prevista, un **tercer registro público QA de administración**, separado de SPA/API consumidoras, puede solicitar permisos Graph delegados mediante login interactivo del administrador. Sin secreto ni M2M; consentimiento limitado al administrador QA, scopes anteriores más lectura de usuarios cuando corresponda. IDs/configuración pública solo en `.local/qa-inventory.json` ignorado. Borrar grant, service principal y registro al retirar QA. Se requiere intervención humana si no existe SSO utilizable; tener un app registration no acredita token/permiso ejecutado.

Tras confirmación del titular de que no hay cliente Google QA, se intentará preparar el proyecto `mikompri-010-spike-20261030`, nombre «MiKompri 010 QA spike», **sin vincular billing ni activar APIs de datos**, OAuth External en Testing, scopes openid/email/profile únicamente, cliente web «MiKompri 010 QA CIAM». Credencial Google, si se crea, solo en configuración protegida CIAM y archivo privado `%LOCALAPPDATA%/MiKompri/qa-010/google-client.json`, fuera del repo y sin stdout. No compartir secretos mediante herramientas de evidencia, capturas o chat. La lista de redirects públicos QA ya está en `.local/google-redirects.txt` ignorado. Eliminar/revocar cliente y solicitar borrado del proyecto al retirar QA. No completar login, captcha o prueba del titular por suplantación; si se requieren, pedir intervención humana y continuar trabajo independiente.

Observación posterior de ejecución: la solicitud generada por el proveedor CIAM incluyó también `address`, aunque la intención inicial era openid/email/profile. No se añadió un campo de dirección MiKompri ni se persistieron atributos de dirección en el harness/evidencia. Registrar esta discrepancia y minimizar scopes/consentimiento antes de implementación; no interpretar el scope observado como nueva necesidad de perfil. [Solicitud saneada](google-federation-request.json).

Continuación autorizada tras aviso «listo»: el titular elimina el bloqueo2SV y se crea el proyecto QA. El botón de actualización de ID regeneró el ID introducido: se conserva ese único proyecto recién creado con el nombre previsto, sin crear un duplicado para corregir un identificador inmutable. El ID efectivo y propósito se guardan en `.local/google-inventory.json`, ignorado; usar ese inventario para OAuth y limpieza. La identidad/roles del tenant productivo no se alteran. Contactos Google obligatorios se seleccionan de la cuenta administrativa del titular dentro de la consola y no se copian a evidence.

Preparación previa del negativo Google directo: añadir al **mismo cliente QA** el origen JavaScript exacto `http://localhost:55412`, sin cambiar callbacks CIAM ni crear otro cliente/secreto. Propósito: Google Identity Services emite un ID token real en una página local aislada; el harness comprueba su firma Google exclusivamente como diagnóstico y acredita que la política API CIAM lo rechaza401. No se añade esquema Google a las APIs de negocio ni correlación de dominio. Coste: mismo MAU/core, sin hosting/API Google de datos. Credencial: solo client ID público en config local/harness; el secreto no se sirve al navegador. Limpieza: origen se retira al eliminar cliente QA; página/proceso local se cierran. Este control no acredita G3 ni habilita linking.

Comprobar disponibilidad de nombre y API oficial; crear solo nombres nuevos y etiquetados de esta tabla. Si ARM/Entra exige rol, MFA, reautenticación o términos humanos, registrar el código saneado y el paso exacto; no modificar políticas para sortearlo. Google requiere control de un proyecto y cuentas QA por su titular. La ausencia de cualquiera de ellos mantiene G1/G3 inconclusos; un JWT sintético no los acredita.
